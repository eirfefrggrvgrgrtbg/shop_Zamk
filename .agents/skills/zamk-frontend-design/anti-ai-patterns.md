# Anti-AI Design Rules

This document explicitly identifies common AI UI failure modes and workflow anti-patterns. Agents must avoid these patterns to prevent ZAMK from looking like a generic, unconsidered "startup template" or violating product workflow boundaries.

---

## 1. WORKFLOW & PROCESS ANTI-PATTERNS

### IMPLEMENTATION CREEP
- **What it is**: Silently advancing from design exploration / mockups into production code, tests, or API types during a design-only phase without explicit Product Owner authorization.
- **Why it breaks workflow**: It violates the DESIGN-ONLY = REPOSITORY READ-ONLY rule, pollutes the repository with unapproved code, creates review confusion, and risks shipping interface fiction before product/business alignment.
- **What to do instead**: Strictly adhere to phase locking. When visual artifacts (HTML prototypes in `<appDataDir>/brain/...` or `/tmp`) are created, STOP immediately, declare `PHASE: DESIGN-ONLY COMPLETE`, and wait for explicit owner implementation instruction.

### IDEAL-DATA THEATER
- **What it is**: Designing UI layouts, charts, and tables that look good ONLY with evenly distributed, perfectly formatted demo numbers (e.g., 10 campaigns with round figures, balanced percentages, uniform label lengths).
- **Why it fails**: Real operational data is messy: 0 records, 1 record with 58 398 ₽, long names, zero conversions, missing attribution. In production, ideal-data layouts collapse, overlap, render `NaN`/`undefined`, or produce giant empty voids.
- **What to do instead**: Stress-test every design against all 5 data realities: **Zero**, **Sparse**, **Normal**, **Dense**, and **Anomalous**. Ensure charts don't crash or distort on 0 or 1 point, tables handle single rows elegantly, and labels wrap or truncate gracefully.

## 2. COMPOSITION & LAYOUT ANTI-PATTERNS

### CARD SOUP
- **What it is**: Many independent rounded white cards placed adjacently, every KPI isolated, resulting in no overall composition.
- **Why it looks generic**: It treats layout as just a grid of boxes rather than organizing information by relationship and priority.
- **What to do instead**: Group related metrics or data into cohesive panels using background shifts, dividers, or layout proximity. Use unified summary regions.
- **Exceptions**: Legitimate dashboard overviews where discrete, distinct widgets represent entirely unrelated systems.

### GENERIC SAAS HERO
- **What it is**: A big title, a gray subtitle, a purple primary button, and an enormous empty space on the right side.
- **Why it looks generic**: It's the default scaffolding generated by automated tools that lack context about what the page actually does.
- **What to do instead**: Design the header area to be functional. Include relevant aggregate data, contextual actions, filters, or meaningful breadcrumbs.

### GENERIC ADMIN TABLE
- **What it is**: Basic filters, a bordered white table, generic "Подробнее" (Read more) links, no internal hierarchy, and no meaningful visualization of data.
- **Why it looks generic**: It mirrors the raw database schema directly to HTML without UX consideration.
- **What to do instead**: Treat the row as a designed component. Combine primary/secondary text (e.g., Name + Email), use status badges, align numbers correctly, and provide row-level contextual actions.

### HUGE EMPTY WHITESPACE
- **What it is**: Massive gaps between elements that serve no structural purpose.
- **Why it looks generic**: It shows an inability to handle variable data density or screen sizes correctly.
- **What to do instead**: Ensure whitespace is used to group related items. If a screen is empty, adjust the max-width or introduce a better zero-state design.

### NATIVE FORM WALL
- **What it is**: A long vertical list of labels, inputs, and selects with no grouping, interaction design, or progressive disclosure.
- **Why it looks generic**: It's the path of least resistance for CRUD applications.
- **What to do instead**: Break forms into logical sections. Use column layouts where appropriate. Provide contextual help text.

### MODAL FOR EVERYTHING
- **What it is**: Putting every create, edit, or delete action into a centered modal dialog.
- **Why it looks generic**: It strips away context and creates a disjointed user journey for complex tasks.
- **What to do instead**: Use inline editing, side drawers (only when underlying context is useful), or dedicated pages for complex operations. Reserve modals for quick, terminal decisions (e.g., confirmations).

## 3. STYLING & DECORATION ANTI-PATTERNS

### PILL ABUSE
- **What it is**: Wrapping every status, filter, and action inside rounded pill-shaped containers.
- **Why it looks generic**: It creates visual noise and gives everything the exact same visual weight.
- **What to do instead**: Use pills strictly for distinct semantic states (e.g., Status: Active). Use plain text, subtle icons, or standard buttons for actions and filters.

### ROUNDED-XL EVERYWHERE
- **What it is**: Applying excessively large border radii to every element on the screen.
- **Why it looks generic**: It attempts to make an interface look "friendly" or "modern" without structural justification, often conflicting with dense data needs.
- **What to do instead**: Use tight, functional border radii (e.g., 4px - 8px) for operational UI, saving larger radii for distinct modal sheets or promotional hero cards.

### SHADOW-SM EVERYWHERE
- **What it is**: Adding drop shadows to every container, input, and button.
- **Why it looks generic**: It muddies the interface and destroys the concept of elevation.
- **What to do instead**: Use flat designs with subtle borders or background color shifts for grouping. Reserve shadows strictly for floating elements (popovers, modals, dropdowns).

### DECORATIVE GRADIENTS
- **What it is**: Unmotivated color gradients applied to backgrounds, buttons, or charts.
- **Why it looks generic**: It is a superficial attempt at "design polish" that distracts from the data.
- **What to do instead**: Rely on solid brand colors (ZAMK violet) or neutral semantic colors.

### GLASSMORPHISM WITHOUT PRODUCT REASON
- **What it is**: Using heavy background blur and semi-transparent layers everywhere.
- **Why it looks generic**: It severely harms performance and readability for the sake of a trend.
- **What to do instead**: Use solid backgrounds for data. Reserve glass/blur effects strictly for sticky headers or floating command palettes where spatial context matters.

### ICON CONFETTI
- **What it is**: Placing an icon next to every single menu item, button, and header.
- **Why it looks generic**: When everything has an icon, nothing stands out. It creates visual clutter.
- **What to do instead**: Use icons purposefully for primary navigation, ambiguous actions without labels, or warnings. Let strong typography handle the rest.

### TINY MUTED TEXT EVERYWHERE
- **What it is**: Defaulting secondary information to 12px or 13px light gray text.
- **Why it looks generic**: It fails accessibility contrast and assumes secondary data isn't actually meant to be read.
- **What to do instead**: Increase contrast. Use regular sizes but shift color to a legible dark gray, or use standard text size with a lighter font weight.

### COLOR AS THE ONLY SIGNAL
- **What it is**: Relying solely on a red/green dot or text color to communicate state.
- **Why it looks generic**: It is inaccessible to color-blind users and easy to miss in dense UIs.
- **What to do instead**: Pair color with text labels, icons, or positional changes (e.g., "Active" badge with a checkmark).

## 4. DATA & ARCHITECTURAL ANTI-PATTERNS

### PLACEHOLDER DASHBOARD / DATA FICTION
- **What it is**: Arbitrary charts, fake metrics, and fake graphs that don't correlate to real backend capabilities.
- **Why it looks generic**: It designs a fantasy product instead of the real one.
- **What to do instead**: Only design surfaces that the current backend APIs can accurately populate. If a feature is conceptual, explicitly tag it `REQUIRES PRODUCT/BACKEND DECISION` or `REQUIRES FUTURE ENDPOINT`.

### DATABASE UI
- **What it is**: Directly exposing UUIDs, raw database IDs, raw enum names (`STATUS_IN_PROGRESS`), and technical internal state to humans.
- **Why it looks generic**: It forces the user to understand the system architecture to do their job.
- **What to do instead**: Map enums to human-readable labels. Use searchable entity pickers instead of asking for UUIDs. Hide technical IDs unless strictly required for debugging/support.
