# ZAMK Backend Check

Цель: после правок backend выяснить, что сломано или рискованно, и честно отделить выполненные проверки от предположений. Общие правила — AGENTS.md, CLAUDE.md и `.claude/rules/` (БД и миграции, финансы и склад), здесь они не повторяются.

Контекст проверки: $ARGUMENTS

Skill ничего не исправляет и не коммитит. Миграции, `psql`, запись в рабочую базу `zamk`, `finalize.sh`, установка зависимостей — запрещены. Остановиться на первой реальной обязательной ошибке; дальнейшие обязательные проверки отметить как «не выполнено».

## 1. Определить область

- `git status --short` и `git diff --name-only` (плюс `git diff --stat`), оставить только `backend/`. Неотслеживаемые файлы тоже учитывать.
- Получить список пакетов `backend/internal/<pkg>` и отдельно: `backend/migrations`, `backend/cmd`, `router`, файлы `dto.go`/`model.go`.
- Если `$ARGUMENTS` называет другие файлы, добавить их и пометить источник.
- Если изменений в `backend/` нет, вердикт PARTIAL «нечего проверять» без запуска команд.

## 2. Ревью diff по рискам (обязательно, до запуска команд)

Читать изменённый код, а не только запускать команды. Для каждого пакета смотреть релевантное:

- **payouts, леджер**: запись `sale_gross`/`zamk_commission`/`seller_earning` идемпотентна (повторный вызов или второй путь не дублирует запись), всё в одной транзакции, суммы в `int64` копейках, округление явное, ошибки не проглатываются, удержание за возврат не превышает остаток.
- **selleranalytics**: формулы и определения не менялись без одобрения владельца; фильтр `seller_id` во всех запросах; проверка владения товаром; пагинация и сортировка валидируются; деление на ноль и NULL; когортные определения возвратов не смешаны с календарными без пометки.
- **inventory, supplies, fulfillment, returns, orders, payments**: `available = total − reserved`, резервы и аллокации ZMU не нарушены, физические операции только у admin с permission (продавец read-only), возврат физический и финансовый разделены, события наблюдаемости эмитятся после коммита.
- **products (stock_forecast)**: статусы платежей, окна и пороги согласованы с аналитикой; не менять формулы без задачи.
- **router, auth**: у новых маршрутов есть роль и permission, `RequireActiveSeller` там, где нужен; есть/обновлены тесты авторизации.
- **migrations**: новая миграция вперёд с новым номером и парной `down`, закоммиченные не редактированы, нет разрушительных операций без явного одобрения, нет переноса UUID окружения.
- **DTO/контракты API**: если менялись JSON-теги, имена или типы в `dto.go`, найти потребителей в `apps/seller/src/api` (и `packages/api-client`) и сообщить о расхождении. Frontend не править.

Каждое замечание давать как «подтверждено (файл:строка)» или «предположение».

## 3. Статические проверки

Из корня репозитория, по одной команде:
- `gofmt -l <изменённые .go файлы>` (непустой вывод — замечание);
- `go vet ./internal/<pkg>/...` для затронутых пакетов (внутри `backend`; использовать `cd backend && ...` только если разрешения позволяют, иначе запросить подтверждение);
- `go build ./...` для backend (или `npm run build:backend` как эквивалент для `cmd`).

## 4. Тесты

Сначала без БД: `go test ./internal/<pkg>/ -run <имена> -count=1` только для тестов, которые не подключаются к БД, подбирая `-run` по изменённым функциям и новым тестам. Тесты с БД (TEST.DB.5):
1. Запускать только через `backend/scripts/safe_go_test.sh ./internal/<pkg>/ -- -run '<имена>' -v` (или `npm run test:backend -- ./internal/<pkg>/ -- -run '<имена>' -v`). Runner сам создаёт disposable-БД и удаляет её. Прямой `go test` с `TEST_DATABASE_URL` запрещён, `zamk_test` тестам не давать.
2. Если runner отказал (нет пакетов, не создана disposable-БД, сработал static guard), DB-тесты **не запускать** обходным путём (BLOCKED для этой части).
3. Запускать только целевые пакеты, затем прочитать вывод: `SKIP` из-за отсутствия БД — это **не пройдено**.

Правила:
- Полный набор тестов проекта не запускать. `npm run test:backend` без явных пакетов отказывает; набора по умолчанию нет.
- Не запускать `backend/scripts/test_migrations_clean.sh` без явной просьбы (он пересоздаёт тестовую базу).
- Если нужного теста нет (например, идемпотентность нового пути записи), не придумывать и не писать его в рамках проверки: перечислить как пробел и предложить тест.

## Отчёт

На русском, коротко:
1. Область: пакеты и файлы (источник списка).
2. Выполнено: команда → результат (PASS/FAIL, число тестов, SKIP).
3. Не выполнено и почему.
4. Замечания ревью: подтверждено / предположение.
5. Непроверенные риски (tenant isolation, идемпотентность, регрессии формул, контракт API) — по каждому статус.
6. Вердикт:
   - **PASS** — все применимые проверки выполнены и прошли, DB-тесты реально выполнены (не SKIP) через `safe_go_test.sh` на disposable-БД, ревью не нашло открытых серьёзных рисков;
   - **PARTIAL** — проверки прошли, но что-то из применимого не выполнено (нет DB-теста, пропуски, предположения по рискам);
   - **BLOCKED** — ошибка сборки, vet, тестов, нарушена защита БД, нельзя подтвердить disposable-БД или обнаружен серьёзный дефект.

После отчёта остановиться, исправления не начинать.
