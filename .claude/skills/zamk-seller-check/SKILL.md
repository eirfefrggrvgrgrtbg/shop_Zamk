# ZAMK Seller Check

Цель: после правок `apps/seller` и `packages/api-client` проверить типы, контракт с backend, финансовое отображение, состояния экрана и сборку, честно отделив выполненное от предположений. Общие правила — AGENTS.md, CLAUDE.md и `.claude/rules/seller-ui.md`, здесь они не повторяются.

Контекст проверки: $ARGUMENTS

Skill ничего не исправляет и не коммитит. Не запускать `npm install`/`npm ci`, не менять конфиги и lock-файлы, не трогать backend. Визуальную приёмку делает Product Owner, не агент: «выглядит правильно» без его подтверждения не утверждать. Остановиться на первой реальной обязательной ошибке; дальнейшие обязательные проверки отметить как «не выполнено».

## 1. Определить область

- `git status --short` и `git diff --name-only`, оставить `apps/seller/` и `packages/api-client/`. Неотслеживаемые файлы и тесты учитывать.
- Разделить на: страницы, компоненты, API-слой (`src/api`), утилиты форматирования (`src/lib`), тесты.
- Если `$ARGUMENTS` называет другие файлы, добавить и пометить источник. Если изменений нет — PARTIAL «нечего проверять» без запуска команд.

## 2. Ревью diff (до запуска команд)

Читать код. Каждое замечание — «подтверждено (файл:строка)» или «предположение».

- **Контракт API**: для изменённых типов в `src/api` сверить поля, имена и nullability с Go DTO (`backend/internal/<module>/dto.go`, только чтение нужной структуры). Расхождения имён, `number | null` против обязательного поля, лишние `as any`/приведения — замечания.
- **Финансовые данные**: деньги приходят в копейках, показываются в рублях через общий форматтер (`formatCents` в `src/lib/utils.ts`), без новых самодельных форматтеров и без ручного деления в компонентах; проценты, return rate, дни покрытия и итоги приходят с backend — frontend их не пересчитывает и не определяет заново; «нет данных» (null) отличается от нуля; единицы и подписи не вводят в заблуждение (например, когортный и календарный процент).
- **Состояния экрана**: loading, error (с повтором), empty; поведение при смене периода или параметров; нет падения на null и пустых массивах.
- **UI/UX и дизайн**: соответствие существующим компонентам и стилям ZAMK Seller (спокойный премиальный вид, не ERP); без `alert()`/`confirm()`; без показа UUID, сырого JSON, копеек и внутренних идентификаторов; без хардкода справочников, которые отдаёт backend; прямые числовые поля вместо +/-.
- **Типобезопасность**: нет `any`, нет подавления ошибок без причины, строгие union-типы там, где backend отдаёт фиксированный набор.
- **Тесты**: у каждого изменённого компонента или функции есть тест на нормальный путь, loading/error/empty и граничные значения денег; новые тесты не опираются на моки как на доказательство бизнес-логики.

## 3. Проверки

Из корня репозитория, по одной команде:
1. Целевые тесты: `npm run test --workspace=seller -- <пути изменённых тестов или компонентов>`; если изменений в тестируемых файлах много, затем весь пакет: `npm run test --workspace=seller`.
2. TypeScript и сборка: `npm run build --workspace=seller` (выполняет `tsc -b && vite build`). Сборка создаёт `dist`, он в `.gitignore`; после запуска убедиться через `git status --short`, что новых файлов не появилось.
3. Линт: `npm run lint --workspace=seller`. Он **не входит** в `npm run check:seller`; результат отдельный. Ошибки в файлах, которых нет в diff, считать ранее существовавшими и сообщать, но не как провал изменений.
4. `npm run check:seller` (тесты + сборка) использовать, если изменено много файлов или затронут `packages/api-client`; он не заменяет линт и ревью.

Если затронут `packages/api-client`, проверить также потребителей в `apps/admin` и `apps/shop` по импортам (чтение) и сообщить о риске; их тесты и сборки не запускать без просьбы.

## Отчёт

На русском, коротко:
1. Область: файлы (источник списка).
2. Выполнено: команда → результат (PASS/FAIL, число тестов, ошибки TypeScript).
3. Не выполнено и почему.
4. Замечания ревью: подтверждено / предположение.
5. Непроверенные риски: расхождение с backend DTO, отображение денег, состояния, визуальное соответствие (нужна приёмка Product Owner).
6. Вердикт:
   - **PASS** — применимые тесты, `tsc`/build прошли, линт не добавил ошибок в изменённых файлах, ревью не нашло открытых серьёзных замечаний; визуальная приёмка оговорена как за Product Owner;
   - **PARTIAL** — проверки прошли, но чего-то применимого нет (нет тестов, линт не запускался, предположения по контракту или деньгам);
   - **BLOCKED** — падают тесты, `tsc` или сборка, обнаружено расхождение контракта или искажение финансовых данных.

После отчёта остановиться, исправления не начинать.
