# Seller Onboarding Flow

## Введение
Этот документ описывает процесс подключения нового продавца к платформе ZAMK. Поскольку открытая самостоятельная регистрация продавцов отключена (по требованиям бизнеса), весь процесс инициируется администратором. 

## Жизненный цикл статусов продавца

Продавец в системе может находиться в одном из следующих статусов:
1. `pending_setup` — (Новый) Продавец только что создан администратором, но еще не заполнил профиль магазина (название, URL, описание, контакты).
2. `pending` — Продавец завершил онбординг (заполнил профиль) и ожидает ручной активации (проверки) модератором/администратором.
3. `active` — Продавец проверен и активирован. Может полноценно продавать товары и выводить средства.
4. `blocked` — Продавец заблокирован за нарушения.
5. `archived` — Продавец архивирован (удален).

### Системный продавец ZAMK
Существует встроенный системный продавец `ZAMK` (id: `00000000-0000-4000-8000-000000000000`), который отвечает за прямые продажи платформы. Он создается миграцией `000030` сразу со статусом `active` и не проходит онбординг.

## Пошаговый флоу подключения

### Шаг 1. Создание продавца администратором
1. Админ заходит в панель управления (Admin Frontend) в раздел "Продавцы".
2. Нажимает "Создать продавца".
3. Указывает `Owner Name`, `Owner Email`, `Brand Name` и базовое описание.
4. Вызывается эндпоинт `POST /api/admin/sellers`.
5. Backend:
   - Хеширует временный пароль для владельца.
   - Создает `User` с ролью `Seller` и флагом `MustChangePassword = true`.
   - Создает `Seller` со статусом `pending_setup`.
   - Привязывает `User` к `Seller` через таблицу `seller_users` с ролью `owner`.

### Шаг 2. Первый вход продавца
1. Продавец заходит на страницу входа Seller Frontend.
2. Вводит свой email и временный пароль.
3. Backend аутентифицирует пользователя и видит `MustChangePassword = true`.
4. Продавца принудительно перенаправляют на форму смены пароля.
5. Продавец меняет пароль (`POST /api/auth/change-password`).

### Шаг 3. Онбординг (Мастер настройки профиля)
1. Продавец попадает в защищенную зону (`SellerLayout`).
2. При загрузке приложения запрашивается профиль (`GET /api/seller/me`).
3. Если `Seller.Status == "pending_setup"`, Frontend блокирует доступ к дашборду и принудительно редиректит на `/onboarding`.
4. На странице `/onboarding` продавец видит пошаговый мастер:
   - **Шаг 1**: Ввод/уточнение названия магазина, URL (slug), описания и контактов (Email, телефон). Данные сохраняются через `PATCH /api/seller/me`.
   - **Шаг 2**: Ознакомление с комиссиями и условиями платформы.
5. Продавец нажимает "Завершить настройку".
6. Вызывается `POST /api/seller/onboarding/complete`.

### Шаг 4. Обработка CompleteOnboarding на Backend
Эндпоинт `POST /api/seller/onboarding/complete`:
1. Извлекает `userID` из JWT токена.
2. Находит магазин, связанный с этим `userID`.
3. Проверяет, что текущий статус именно `pending_setup`. Если нет — возвращает ошибку (защита от повторного прохождения или изменения активных магазинов).
4. Переводит `status` в `pending`.
5. Возвращает `204 No Content`.

### Шаг 5. Активация администратором
1. Магазин продавца теперь имеет статус `pending`.
2. Продавец перенаправляется в Dashboard, где видит сообщение, что его аккаунт проверяется администрацией.
3. Админ заходит в Admin Frontend, видит продавца со статусом `pending` ("Ожидает активации").
4. Админ может изучить заполненные продавцом данные (описание, контакты) и нажать "Проверить и активировать".
5. Вызывается `POST /api/admin/sellers/{id}/verify`.
6. Статус магазина меняется на `active`.
7. Продавец может публиковать товары.

## Безопасность
1. **Изоляция:** Продавец не может управлять чужим магазином, так как `seller_id` всегда жестко берется из привязки пользователя (JWT -> `userID` -> `seller_users` -> `seller_id`).
2. **Защита стейт-машины:** Эндпоинт завершения онбординга жестко проверяет, что текущий статус равен `pending_setup`. Если продавец уже `active` или `blocked`, онбординг не отработает.
3. **Разделение полномочий:** Смена статуса с `pending` на `active` доступна только пользователям с RBAC-правом `sellers.verify` (Администратор платформы).
